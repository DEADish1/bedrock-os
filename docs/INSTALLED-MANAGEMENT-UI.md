# Installed management UI

The hosted preview build remains `npm run build`. The OS-oriented entry uses the same `app/page.tsx` client component and `app/globals.css`, but has a separate static build with no Cloudflare/Sites runtime or server-side rendering requirement.

```
npm ci
npm run build:installed-ui
npm run test:installed-ui
npm run typecheck:installed-ui
```

Output is `dist/management-ui/`: HTML, hashed JavaScript/CSS, the lazily loaded noVNC console bundle, and public branding assets. The installed entry uses system font fallbacks and does not download fonts at runtime. Asset checks verify local references, required files, the guest-console chunk, and absence of source maps. They are not browser-rendering or API integration tests.

Do not expose this directory as an unauthenticated substitute for a management gateway. The UI already uses same-origin `/api/v1` requests; the packaged backend currently serves a Unix socket. Checklist 0.6.3 still requires OS image packaging, an HTTP(S)/WebSocket gateway, explicit TLS/trust and local access policy, authentication, origin/CSRF enforcement, limits/timeouts, service lifecycle integration, and clean-installed-server/browser acceptance. No gateway or LAN listener is enabled by this build command.

The installed TypeScript check covers the shared UI, its noVNC declaration, the browser entry, and its build configuration. It does not replace repository-wide checking: on 2026-09-27, `npx tsc --noEmit` reported existing browser-test type errors in `tests/e2e/management.spec.ts` (Playwright Page compatibility at line 156 and narrowed request fields at lines 266-268). These remain open under repeatable management CI, 0.6.9.

## Image build integration

`os/scripts/build-image.sh` runs `build-installed-ui.sh` before live-build. The UI is built in a temporary source-only workspace using checksum-pinned Node 24.16.0 Linux x64 and `npm ci` from the repository lockfile; the existing working tree's node_modules is not changed. The Node archive checksum is pinned from the [official release checksums](https://nodejs.org/dist/v24.16.0/SHASUMS256.txt). Network access is required for this build step, not for serving the installed assets.

The generated `/usr/share/bedrock/management-ui/build-manifest.json` records the source commit, Node version, lockfile digest, and each asset's size and SHA-256. Staging refuses to overwrite an existing directory. The image build checks the staged manifest, extracts the UI from the ISO, verifies all files, and compares the embedded manifest with the source build's expected manifest. The raw-image builder uses the same live-build root filesystem. Generated staging and temporary toolchain files are removed after use; the UI remains inside the image. Linux build/ISO/reproducibility validation is pending for this integration.

`os/tests/test-installed-ui-manifest.py` exercises wrong source commits, corrupted contents/sizes, traversal, duplicate entries, unexpected files, and symlinks. The complete test requires Linux symlink support; local Windows verification passed for the real bundle, but the test suite stopped at the restricted symlink operation. Gateway configuration, browser rendering, and final npm license/SBOM qualification remain open.

Image packaging passed [run 36349114364 at 04e3ce2](https://github.com/DEADish1/bedrock-os/actions/runs/36349114364): Linux validation, both image builds, embedded UI verification, and reproducibility succeeded. This supersedes the pending integration note above. Physical acceptance was skipped.

## Gateway implementation and remaining acceptance

The packaged `bedrock-web.service` uses nginx under the dedicated `bedrock-web` UID, with no capabilities, a read-only system filesystem, inaccessible persistent Bedrock state, and systemd-delivered TLS credentials. Supplementary API-group membership permits connection to the API Unix socket; the broker independently checks peer UID and does not authorize the gateway account. The ordinary distribution nginx service is guarded off to avoid its default HTTP listener. The Bedrock gateway is not yet enabled automatically by the image.

Current ingress is **HTTPS on 127.0.0.1:8443 only**, with exactly `localhost:8443` and `127.0.0.1:8443` accepted as Host values. Unexpected Origin values, opaque `null` origins, and cross-site Fetch Metadata are denied. Requests without Origin remain usable by non-browser clients; API authentication still requires the existing bearer token. Cookies are not forwarded. This is not finished LAN access or first-run setup.

The proxy forwards only to `/run/bedrock-api/api.sock`; it does not expose the action broker. HTTP Authorization and ETags are preserved. WebSocket upgrade forwarding follows the [nginx WebSocket proxy guidance](https://nginx.org/en/docs/http/websocket.html), retaining the original Host for the API's Origin checks. Buffering and temporary response storage are disabled per the [proxy-module configuration](https://nginx.org/en/docs/http/ngx_http_proxy_module.html). Ordinary bodies are limited to 64 KiB; the guarded image-upload path permits the existing 4 TiB API maximum. There are 16 concurrent connections per source, bounded header/idle timers, a 120-second ordinary upstream read timeout, and a one-hour idle timeout for console connections. No access log is written; request contents and credential-bearing headers must not be logged.

The identity helper generates a unique P-256 self-signed localhost certificate on first use and preserves it across restarts. The key is root-private and supplied to the gateway through `LoadCredential`, not bundled into images. Existing expired, indirect, or mismatched identities fail closed. Trust requires explicit fingerprint verification/provisioning; the tests trust only the generated fixture certificate and do not disable TLS verification. Owner-facing trust enrollment, renewal/rotation, LAN host/address configuration, and first-run service activation remain unfinished. HSTS is intentionally not imposed on the shared localhost hostname.

`test-web-gateway.py` runs inside the disposable systemd fixture against the real API, covering TLS verification, authentication/denial, Host/Origin checks, request limits, hidden paths, invalid WebSocket handshakes, distribution-HTTP suppression, unprivileged execution, and certificate reuse. Its HTML is a small transport fixture, not evidence that the bundled React UI renders or that a valid guest-console stream works. Validation is pending in [run 36370749784 at dfe3858](https://github.com/DEADish1/bedrock-os/actions/runs/36370749784). Checklist 0.6.3 remains open.

## Guided local access setup (partial)

`sudo bedrock-setup-management` now provides a root-terminal dialog menu for named token issuance, certificate SHA-256 fingerprint display, and local HTTPS enable/disable. It refuses redirected input/output. Tokens are written only to a mode-0600 file in a private temporary `/run` directory for display, not to dialog arguments or subprocess error messages. Cancelling the display revokes the newly issued token; normal exit removes the temporary file. Existing token names are not overwritten. Enabling requires an unrevoked token and starts/checks the service before enabling its boot startup. Disabling preserves tokens and identity. This remains loopback-only, not LAN provisioning.

Seven setup unit tests and the existing real gateway suite passed [validation at 6530b60](https://github.com/DEADish1/bedrock-os/actions/runs/36372535499/job/108771658841). Unit coverage includes cancellation, invalid names, private-file cleanup, revocation on display cancellation, and activation ordering/failure; helper/service calls are mocked in these setup unit tests. The dialog menu itself still needs real-console acceptance and integration with the first-run wizard. Token rotation/recovery/revocation UI, renewal, LAN trust/address policy, and terminal-free first-run handoff remain open. The previous statement that no guided gateway setup exists is superseded only by this partial implementation, not by completion of 0.6.3 or 0.6.4. Image builds for this source revision are pending.
