# Bedrock local management API

Bedrock exposes a versioned, authenticated management API only through the local Unix socket `/run/bedrock-api/api.sock`. The service does not bind a TCP port. A future web gateway may access the socket after it authenticates the browser session and applies its own authorization policy.

## Authentication

Create a client token as root with `create-api-token NAME`. The command displays the 64-character bearer token once. Bedrock stores only its SHA-256 digest in `/var/lib/bedrock/api/tokens.json`; the state is bounded to 16 uniquely named tokens and is readable only by root and the API service account.

Use `manage-api-tokens list` to inspect token names, creation times, and revocation status without exposing hashes. Use `manage-api-tokens revoke NAME` to atomically invalidate a token. Revocation takes effect on the next request and cannot be silently repeated.

Send the token as `Authorization: Bearer TOKEN`. Missing, malformed, unknown, or revoked credentials receive `401`. API responses must not be cached.

## Version 1 foundation

- `GET /api/v1/health` reports API availability.
- `GET /api/v1/openapi.json` returns the authenticated OpenAPI 3.1 contract for every implemented v1 route.
- `GET /api/v1/dashboard` returns privacy-safe hardware, storage, alert, VM, and update summaries. Each component has an independent availability state, so stale or malformed subsystem data cannot suppress healthy telemetry from the others.
- `GET /api/v1/virtualization/capabilities` returns the existing fail-closed virtualization capability report, or `503` while that report is unavailable.
- `GET /api/v1/tasks` returns at most 256 bounded task records with monotonic timestamps and validated progress. It excludes command arguments, paths, user labels, and error text.
- `GET /api/v1/alerts` returns active alert identity, kind, severity, and timestamps without exposing device paths or other resource identifiers.
- `GET /api/v1/audit` returns the newest 100 events from a bounded append-only feed. Events expose only a stable identity, category, action, outcome, and timestamp.
- `GET /api/v1/remote/devices` returns names, lifecycle timestamps, revoked/expired state, and unexpired pending-pairing identifiers from a root-generated privacy-safe view. Public keys, fingerprints, and one-time codes remain inaccessible to the API service.
- `POST /api/v1/remote/pairings/{id}/approve` records server approval for one pending request. It requires a canonical UUID v4 `Idempotency-Key` and the exact phrase `APPROVE REMOTE DEVICE {id}`; approval does not disclose or redeem the one-time code.
- `GET /api/v1/apps` returns configured application identity, networking mode, resource limits, update policy, and creation time from a root-generated privacy-safe view. Registry locations and image digests remain inaccessible to the API service.
- `POST /api/v1/apps/{id}/power` starts or gracefully stops an installed isolated application after a canonical UUID v4 idempotency key and exact `START APPLICATION …` or `STOP APPLICATION …` confirmation. The guarded helper reuses the existing fixed sandbox and publishes refreshed running state without exposing container internals.
- `DELETE /api/v1/apps/{id}` removes the isolated container and its configuration after exact `REMOVE APPLICATION …` confirmation while deliberately preserving the application's data directory for recovery.
- `POST /api/v1/apps/{id}/update` installs the root-discovered candidate digest after exact `UPDATE APPLICATION …` confirmation. The API sees only an availability flag; image repositories and digests remain in root-owned state. The guarded manager restores the prior pinned container if recreation fails.
- `POST /api/v1/apps/{id}/install` installs one root-staged, digest-pinned application after exact `INSTALL APPLICATION …` confirmation. `GET /api/v1/apps` exposes only its safe name, limits, network mode, port count, and update policy; the registry and digest never enter the API request or response.
- `GET /api/v1/backups` returns plan identity, schedule, retention, last-success time, snapshot availability, and safe summaries of root-staged creation candidates. Source paths, repository locations, credentials, initialization choices, and snapshot identifiers remain inaccessible to the API service.
- `POST /api/v1/backups/{id}/create` consumes one exact root-staged plan after exact confirmation. The API supplies only the candidate ID and cannot choose or alter its source, repository, password, schedule, retention, or initialization behavior.
- `POST /api/v1/backups/{id}/run` executes one configured encrypted backup and its retention policy after exact confirmation. It accepts no source, repository, password, or arbitrary command from the API caller.
- `POST /api/v1/backups/{id}/restore-latest` restores the plan's latest successful snapshot into its fixed new recovery destination after exact confirmation. Snapshot identifiers and host paths never cross the API boundary, and an existing destination is never overwritten.
- `POST /api/v1/images/{name}/convert` creates a new verified QCOW2 or raw image from an existing managed disk image. The request binds the source name and SHA-256, requires a unique target name and exact confirmation, and never accepts or returns a host path.
- `PUT /api/v1/images/{name}/upload` streams an authenticated binary ISO, IMG, QCOW2, VHDX, or VMDK into the API service's confined staging directory and returns its server-computed SHA-256 for review. `POST /api/v1/images/{name}/import` requires the exact type, name, and hash confirmation before the root importer independently verifies size, checksum, format, encryption/backing-chain policy, and uniqueness. Successful import removes the staged upload.
- `GET /api/v1/hardware` returns processor, memory, disk capability, storage-controller, network-link, GPU, and USB-count data while omitting device paths, interface names, MAC addresses, PCI/USB topology, numeric vendor/device IDs, serials, and IOMMU membership.
- `GET /api/v1/vms` returns the bounded managed VM inventory with lifecycle state, autostart, assigned CPU and memory, validated logical snapshot names, and logical image/network attachment names. It does not expose disk paths, console sockets, MAC addresses, libvirt XML, or host device topology.
- `POST /api/v1/vms` creates a stopped Q35/UEFI virtual machine with a persistent TPM 2.0, bounded CPU/memory/disk allocation, and optional autostart after exact confirmation. The guarded orchestrator independently rechecks host reservations and virtualization readiness, deterministically renders and hash-binds the definition, registers the disk/domain, and publishes task and audit state.
- `POST /api/v1/vms/{name}/power` performs start, graceful stop, restart, or force-stop only after a canonical UUID v4 idempotency key and the exact name/action confirmation. The root broker creates only the helper's fixed name-bound request and returns no libvirt or command output.
- `POST /api/v1/vms/{name}/snapshots` creates, restores, or deletes an offline managed snapshot after a canonical UUID v4 idempotency key and the exact VM/snapshot/action confirmation. The guarded helper independently requires the VM to be shut off and verifies libvirt state afterward.
- `POST /api/v1/vms/{name}/clone` clones a shut-off, attachment-free VM to a validated new name after exact confirmation. Capacity reservations and output paths are revalidated by the guarded helper.
- `DELETE /api/v1/vms/{name}` moves a shut-off VM and its managed storage into recoverable quarantine after exact `DELETE VM … AND STORAGE` confirmation. The root broker binds the request to the current definition hash; clients never receive host paths or definition contents.
- `POST /api/v1/vms/{name}/resources` updates offline vCPU, memory, and supported boot order after exact confirmation. The guarded helper independently enforces hardware reservations, 256 MiB memory increments, shut-off state, and post-definition verification.
- `POST /api/v1/vms/{name}/images` attaches or detaches a checksum-verified managed image while the VM is shut off. `POST /api/v1/vms/{name}/networks` similarly manages a deterministic virtio interface for an active managed isolated network. Both require a canonical UUID v4 idempotency key and exact VM/item/action confirmation; the guarded helpers verify persistent libvirt state, publish task progress and audit outcomes, and roll back partial mutations.
- `GET /api/v1/images` returns verified managed images plus path-free staged-upload summaries containing only name, format, byte size, and SHA-256. Managed filesystem locations remain inaccessible to clients.
- `GET /api/v1/storage` returns disk capacity and SMART summaries, Linux RAID and ZFS health and rebuild progress, and bounded hardware-RAID visibility counts. Device paths, serial numbers, member patterns, controller addresses, slot identifiers, and vendor descriptions remain inaccessible to clients.
- `POST /api/v1/storage/{id}/scrub` starts a ZFS scrub or Linux RAID consistency check for an existing managed group after exact confirmation. The root wrapper resolves backend and layout from protected state; the API cannot supply device paths or storage commands.
- `GET /api/v1/settings` returns the validated update-check choice and release channel plus the enforced no-automatic-install and telemetry-disabled states. Hostname, account, network, credential, and other first-run configuration remain inaccessible to clients.
- `PUT /api/v1/settings` changes exactly one update-policy field. It requires a canonical UUID v4 `Idempotency-Key`, a strict JSON body, and explicit acknowledgement for the beta channel; identical retries are replayed and conflicting key reuse returns `409`.
- `GET /api/v1/users` returns managed NAS account names, credential-rotation generation/timestamps, and group names with member counts. Passwords, hashes, member identities, datasets, ACLs, share paths, and snapshot names remain inaccessible to clients.
- `POST /api/v1/users` creates a local NAS user or group after exact confirmation. The strict root wrapper builds the full fixed NAS request and accepts no password, shell, numeric identity, home path, or arbitrary account option from the API.
- `POST /api/v1/groups/{id}/members` adds one existing managed NAS user to an existing access group after an identity-bound exact confirmation. The API exposes group member counts, not membership identities.
- `POST /api/v1/users/{id}/rotate-credential` consumes a password previously staged by root with `bedrock-stage-nas-credential`, rotates the managed SMB credential after exact confirmation, and removes the staged secret. Password content never crosses the API boundary.

Malformed, oversized, indirect, or unavailable task, alert, audit, remote-device, application, backup, hardware, VM, image, storage, settings, and user sources fail independently with `503`; the API never returns partially validated records.

Privileged operations publish state through `record-api-task`. The writer serializes updates, rejects identity, timestamp, or progress regression, caps retained tasks at 256, and emits one privacy-bounded audit event when a task reaches a terminal state. Operations may expose stable task identity and kind, counters, and timestamps only; paths, command arguments, user labels, and raw error messages are prohibited.

Verified update downloads publish queued, byte-accurate running, succeeded, and failed states. Resumed bytes count only after the complete artifact passes size and SHA-256 verification, and the final success state is emitted only after the whole signed bundle passes verification.

VM start, stop, force-stop, and restart publish three bounded steps: managed-state and libvirt preconditions verified, the requested command issued, and the expected final power state observed. Task and audit records identify only the action; VM names remain outside the feed.

Storage create, expand, scrub, replace, export, and import operations publish three bounded steps: managed-state and safety preconditions verified, the backend operation completed, and durable state plus the existing storage audit committed. Task records identify only the operation kind; pool names and device paths remain private.

All other paths return `404`. Unsupported mutating requests return `405` after authentication. Mutation endpoints delegate to existing guarded Bedrock helpers so their independent precondition checks, exact confirmations, serialization, rollback, and audit boundaries remain authoritative.

The mutation-side privilege boundary is packaged separately from the API. A root action broker listens only on `/run/bedrock-action-broker/action.sock`, authenticates the kernel-reported peer as the `bedrock-api` account, accepts strict bounded action schemas, and delegates to fixed Bedrock helpers without invoking a shell. Pending and terminal request UUIDs, request hashes, and creation times are retained in a bounded owner-only ledger so interruption recovery is safe, identical successful retries are replayed, and conflicting reuse fails closed. Each policy change publishes a privacy-safe `update-policy` task and exactly one terminal audit event; VM power actions retain the lifecycle helper's existing three-step task and terminal audit boundary. The broker never returns helper output.

The packaged schema is the machine-readable source of truth for interface clients. API tests require its route set and bearer security declaration to match the implementation; undocumented routes and unauthenticated schema discovery are rejected.
